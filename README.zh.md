# dsh-fail-guard

[English](README.md) | 中文

同一工具连续失败 N 次之后，叫停，并把它按四段说清楚。

它做的是**外部打断**：在连续失败达到阈值的那一刻，往对话里推一条停手指令——试过什么、完整错误原文、初判原因、需要用户做什么——这样它会来报告，而不是再试第四种命令写法。

## 它到底在治什么

思考里的复读（「做。做。做。」「Let me… Let me…」）一般不是模型退化。

**是连续试错**：同一件事失败、换参数、再失败，没有新信息进来，于是同一个「该动手了」的决定被反复重下。

在一份 74 轮的会话里实测（2026-10-30）：前 67 轮短句行占比在 7–48% 之间波动，从「用浏览器滚评论区连续失败十几步」那一刻断崖跳到 81.6%，之后是 85.9% / 89.1% / 91.4%。

提示词层的规则（「连续失败两次就停手」）在那个状态下是无效的——**因为那时候模型读的不是提示词，是它自己的 thinking。** 打断必须来自外部。这就是这个插件做的事。

## 安装

```sh
dsh plugin --profile desktop add dsh-fail-guard
```

重启一次 DSH。`cordis.patch.yml` 会通过 `dsh.bundle` manifest 自动应用，不用手写 profile 配置。

## 配置

**配置在「插件 → dsh-fail-guard → 详情」里。** 六个参数都有默认值，空配置也能跑；字段标了 `.volatile()`，**保存即生效，不用重启**。

也可以直接写 `cordis.patch.yml`，效果一样。

所有选项都有默认值，空配置也能跑。

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `threshold` | `2` | 连续失败几次后推停手指令。 |
| `sameToolOnly` | `true` | 按工具分别计数。设 `false` 则任何工具的失败都累加到同一个连续计数里。 |
| `stopText` | 内置 | 被推入对话的那条指令。想换措辞就覆盖它。 |
| `stopSummary` | 内置 | 面板提示里显示的一行摘要。 |
| `debug` | `false` | 把每个事件、每次计数、每次叫停写进日志文件。 |
| `logFile` | `<插件目录>/fail-guard.log` | `debug` 写到哪里。Electron 主进程的 console 从任何地方都读不到，所以文件是唯一能看到「插件到底收到了什么」的方式。 |

在 `cordis.patch.yml` 里覆盖：

```yaml
- id: dsh-fail-guard
  config:
    threshold: 3
    sameToolOnly: true
```

## 失败是怎么判定的

一条 `tool/result` 满足下面任意一条就算失败：

- `message.isError === true`
- `meta.opsShell.exitCode` 存在且非零

两条都要看，因为单独任何一条都不完整：一条退出码为 1 的 shell 命令不会被标 `isError`，而某些工具级错误又不带退出码。

计数器按「会话 + 工具」分组，任何一次成功都会清零。

## 为什么用 `steer` 而不是 `inject`

`inject` 只在面板里显示一条提示，不改变模型下一步做什么。

`steer` 会进入收件箱，被下一步 claim。这跟 `dsh-huanqi` 记录的接口选择一致。

## 它不做什么

- 它不会中止刚刚失败的那次工具调用——那次已经发生了。
- 它不判断这次失败「算不算真失败」；任何非零退出都算。
- 它不重置对话。停手指令只是多了一条用户消息，仅此而已。
- 它不是限流器。如果收到指令后还继续失败，连续计数会重新开始，`threshold` 次之后会再叫停一次。

## 一个实现细节（写插件的人会踩）

`session/event` 是在 **agent 自己的 ctx** 上发出的，挂在插件根 ctx 上收不到 `tool/result`。而且不能两处都挂——Cordis 事件向父 ctx 冒泡，双挂会让计数翻倍，`threshold: 2` 实际等于 1。正确做法是 `ctx.on('agent/created', …)` 之后在 `agent.ctx` 上挂一次，并对 `ctx.agents.list()` 里已存在的会话补挂。
